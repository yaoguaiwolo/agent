## 总任务

给 Agent 加上**上下文长度管理**。

问题背景：记忆是一个列表，每次请求都把**完整列表**发给 API。对话越长 →
每轮消耗的 token 越多（费用暴涨）→ 最终超出模型的上下文上限，直接报错。
目标：让 Agent 在历史变长时自动"瘦身"，同时尽量不丢重要信息。

---

## 任务 0：让问题先"被看见"（必做）

- [x] 每轮对话后，打印这次请求实际消耗的 token 数（AI 代写：`agent_loop` 里每次调用后打印 `[Token] 输入+输出=总计`）

提示：API 返回的 `response` 对象上有个 `usage` 属性，里面有
`prompt_tokens` / `completion_tokens` / `total_tokens` 三个字段，
是服务端算好的精确值，不用自己估算。

**验收现象**：连续聊 10 轮，打印的数字一轮比一轮大——
这就是"记忆 = 全量重发"的直接代价。

---

## 任务 1：滑动窗口（必做）

- [x] 当长期记忆超过阈值时，自动丢掉最老的消息，只保留最近的部分（AI 代写：`trim_messages()` 函数，在保存点调用）

需要自己做的设计决策（想清楚再动手，写进下面的"设计笔记"）：

1. **阈值用什么单位**——消息条数？字符数？token 数？优缺点各是什么
2. **在哪里动手**——两个候选位置：构建 `turn` 之前，或者保存点
   `messages = turn` 附近。选一个，想清楚为什么
3. **阈值常量放哪**——放顶部配置区和 `MEMORY_ON` 做邻居，名字要清楚

---

## 任务 2：自动摘要（进阶，选做但强烈推荐）

- [x] 超限时不再直接丢老消息，而是先发给 LLM 压缩成一段摘要，
      用摘要**替换**被删掉的老消息（AI 代写：`summarize_messages()` + `compact_messages()`）

三个关键点：

1. 摘要是一次**独立的 API 调用**，不带 `tools`；system 提示词要写明
   "你是摘要员，把对话压缩成要点"
2. 摘要放回列表时，想清楚用什么 role、放在哪个位置
3. 摘要调用本身也耗 token——"多频繁压缩"也是一个设计决策

---

## 三个坑（提前知道，踩进去别慌）

1. **system 消息永远不能丢**——它是 Agent 的人设，丢了行为会变得很怪
2. **tool 配对问题**——历史里 `assistant(带tool_calls)` 和紧跟它的 `tool`
   结果是一对，从中间截断的话，下一轮请求 API 直接报 400。
   想清楚怎么保证不拆散一对
3. **摘要调用本身也耗 token**——别陷入"为了省 token 花更多 token"的怪圈

---

## 测试技巧

把阈值故意设得非常小（比如只保留 4 条消息），几轮对话就能触发机制，
不用真的聊到 128K。测完改回正常值。
